# 发令、拨弹和摩擦轮掉速延迟调查

## 后续机械排查结果

用户于2026-10-31现场确认：原进弹链路没有单发限位，弹丸会自行滚入摩擦轮，造成不稳定的等待；加两条电工胶模拟限位后，顺时针预测延时改为200ms，实弹观察接近全中。该反馈为机械随机等待的强证据，具体毫秒分布、真实出膛时刻及独立命中统计仍未测量。后续判断应先以限位后的新机构为准，早先无约束滚动状态不适合再用于标定固定发弹延时。原有被动时间戳方案可用于评估提频后的延时、速度下降和恢复，但没有因此自动安装到固件。

## 已确认的缺口

实际使用的电控工程是 `H:/rm/Sentinel_robot-main(1)/Sentinel_robot-main`。其中 `STM32F405/xuc.cpp` 发送0x01/0x02姿态、0x81许可和0x83任务累计计数，没有发送本视觉仓库可识别的0x82拨弹诊断。不能把视觉仓库中另一份固件的诊断功能当成已烧录功能，更不能整套覆盖实际工程。

小电脑最近3份图像诊断共3927条，观察到66条不同上位机发令记录；拨弹诊断available、有效发令/运动事件以及非零摩擦轮转速记录均为0。缺失值不表示零延迟。原始核对结果保存在小电脑 `logs/shot-latency-observability.json`。

无线调试器ATK 20190528能被本机枚举。本轮没有使用旧RAM地址读取新固件，也没有启动调试或暂停CPU。实时Watch/无线轮询可能漏掉短暂转速下降，不能直接用于精确打点；更适合读取电控已在本地记录的事件。

## 需要分开的时刻

| 时刻 | 定义 | 建议记录位置 |
| --- | --- | --- |
| T_host | 上位机完整write返回 | 现有`XucSender`成功发令日志，Linux单调时钟 |
| T_rx | 携带fire位的有效命令到达MCU | UART接收快照时间，绑定boot/命令seq |
| T_accept | 命令通过校验且本地模式允许 | 实际工程`XUC::HandleAim`末端 |
| T_issue | 控制器实际生成新的拨弹位置目标 | `CONTROL::SHOOTER::Update`改变并限幅setangle之后 |
| T_motion | 编码器及转速首次确认正向拨弹运动 | 对应拨弹电机真实CAN反馈 |
| T_travel | 编码器完成一发所需净行程 | 同一电机累计编码器，单独记录目标误差 |
| T_settle | 拨弹轮到位并低速保持 | 行程/位置误差与速度联合条件 |
| T_sag | 装弹测试中摩擦轮转速显著下降 | 左右摩擦轮真实CAN反馈；保留完整短时曲线 |
| T_recover | 转速恢复并稳定 | 左右轮独立检测后共同确认 |

运动支路为T_issue→T_motion→T_travel/T_settle；摩擦轮支路为T_issue→T_sag→T_recover。不假定T_sag一定发生在拨弹行程完成之后。

摩擦轮掉速是负载事件代理。空载供电波动、控制震荡、弹丸接触持续时间都能影响它；不能直接称为弹丸出膛时刻。没有枪口传感器/高速视频时，应保留这个未知量。

## 时钟和归属

- 所有MCU事件使用现有`TIM::NowUs()`，同一1MHz、32位计数器。时间差用无符号减法处理约71.58分钟回绕，关联窗口保持远小于半个回绕周期。
- 一发使用`boot_id + 命令seq + MCU事件序号`关联；seq会回绕，不跨boot或电机反馈generation混用。连续请求、重复帧、没有实际执行、保护撤销、目标被截断、前发未完成又来了新发，都必须单独标记。
- `HandleAim`当前的`aim_rx_tick`只是任务tick，且非fire帧会覆盖，不是可直接使用的单发微秒记录。`frame_time_us`属于UART快照，可能包含多个协议帧，不能未经核对就称为最后一字节准确时刻。
- Linux单调时间与MCU微秒时钟不能直接相减。第一阶段先测T_rx/T_accept到T_sag等同MCU时钟差。完整T_host到机械事件还需单独估计传输/时钟映射及不确定度；现有约30ms姿态时间不确定度不能用于宣称毫秒精度。
- 38字节下行帧按921600 baud、8N1计算，纯线上传输约0.412ms，不包括USB缓冲、系统调度、UART队列与解码任务等待，也不是实测通信延迟。

## 源码能说明什么

- `taskslist.cpp`：DecodeTask和ControlTask均为5ms周期；MotorUpdateTask为2ms；CAN发送任务为1ms、三路轮流发送。调度/总线正常时，软件各段应在毫秒量级运行，但这些名义周期不能相加当成实测，也不是最坏时延保证。
- `control.cpp`：单次触发上升沿直接减去`para.bullet_step`，没有固定280ms等待。T_ARM=300ms、T_RATE=125ms用于持续触发分支，不等于单发到出膛时间。
- 只有摩擦轮、拨弹电机反馈新鲜、温度、转速和许可等条件满足时才生成拨弹目标。保护失效会取消待执行目标，不能把没有执行的指令作为长延迟样本。
- 当前源码`shoot_speed=6500`、就绪比例0.8、左右速度差限制300rpm；须在采集时记录实际目标值/运行值，不能假设Live Watch或烧录版本完全相同。
- 当前`bullet_step=42130.29`是电机编码器计数行程，不是一圈拨弹盘。累计一发行程和位置闭环完全停稳是两个指标。
- CAN发送采用`HAL_CAN_Transmit(...,10)`。异常/拥塞时有阻塞可能，测量应记录反馈新鲜度和CAN发送失败，不能只根据任务周期排除延迟尖峰。

## 推荐的被动打点方案（待实施）

1. 只在实际固件增加时间戳和固定容量记录，不更改PID、拨弹目标或任何许可。控制和CAN路径不printf、不阻塞等待；原始记录交给低优先级任务或测试后只读导出。
2. 以真实CAN帧到达时间记录编码器、拨弹转速、左右轮转速，并保存每路样本时间/新鲜度。CAN帧之间不同时到达，禁止给三路旧值统一伪造一个“同时采样”的时间。
3. 每发保留短时原始曲线及基线，计算运动、整步行程、位置停稳、左右掉速和恢复。掉速检测先采用可调阈值，例如基线下降3%，并参考空载转速噪声；保留至少两种阈值的敏感性分析，不凭单点毛刺定事件。
4. 记录取消、过期、反馈中断、未就绪、重启、重叠发令等无效原因。记录溢出必须可见，不能静默关联到下一发。
5. 若采用现有0x82诊断扩展，也需补齐完成/掉速事件：仓库中的现成版本只记录request/issue/首次运动及轮速，没有单发完成和掉速专用时间戳。先检查实际工程发送缓存容量和带宽；不覆盖0x83任务状态、不修改既有控制帧，也不依赖50Hz图像诊断抽样保存每个短事件。

## 实测顺序与交付指标

先采无弹、摩擦轮已稳定的拨弹基线，再由操作人员在合适测试环境手动进行有弹单发。第一轮每发间隔建议至少2秒，或等待两轮实际恢复稳定后再触发，取较慢者；这是隔离测量条件，不是改动比赛发令间隔。正常自瞄和任务不应被采集工具自动启动。

有弹先取约20发，随后再取连续发射组，比较首发、后续发、不同目标摩擦轮转速及温度。空载组用于排查拨弹电机耗电引起的假掉速，不能代替有弹测试。

输出每发T_rx→T_issue、T_issue→T_motion、T_issue→T_travel/T_settle、T_issue→左右T_sag、左右最低rpm/掉速幅度、T_sag→T_recover；附有效样本数、被排除原因、时间量化/采样误差及中位数、范围。20发的P90/P95只作探索性描述，不当成稳定尾部统计结论。

完成这些测量后，再评估当前顺时针预测延时，而非用拨弹轮停稳时间直接替换Aimer中的到出膛延时。弹丸飞行时间仍是另一个独立项，不能重复加入。
