## 结论与边界

用户已确认固定装甲板命中正常，旋转装甲板的真实弹丸仍常出现在运动前方。此次检查发现并修复了一处可离线复现的发射时钟校准缺陷：相位误差过大时，周期和相位校准一并被拒绝，程序仍按旧时钟发送。这个缺陷能够解释持续漂移、调参效果不稳定；目前不能证明它解释了全部方向性脱靶。

## 1. 已确认并修复：大相位误差让校准卡住

位置：`tasks/auto_aim/gyro_phase_scheduler.hpp` 的 `FixedCadenceTrigger::calibrate()`。

原逻辑在完成多次过中心事件拟合后，如果拟合锚点与旧时钟的差超过单面周期的 1/4，直接 `return`。单面 90°，因此门槛为 22.5°。这会同时丢弃可信周期更新。

后果：

1. 时钟先因初始偏差、过中心噪声或周期误差发生漂移。
2. 漂移超过门槛后，新事件虽然不断到来，校准更新次数仍长时间不变。
3. 发令按旧时钟继续；程序内部计算的发令相位仍很准，但它已经偏离最近的视觉模型。
4. 真实周期完全固定时，这个代码问题仍然可能发生。

实测记录 `vision-1792881396133803.jsonl`：第 8 次发令时更新次数为 2；之后约 21 秒仍为 2。期间视觉/时钟相位差由约 27° 增长至接近 ±45°；约第 37 次发令才重新出现校准更新。此处角度是视觉模型与调度时钟的差，不是实测靶板角度真值。

修复保持多事件拟合、设定周期 ±10% 范围、每次周期变化最多 0.5%、锚点每次移动最多 3 ms。去掉“大相位差连周期更新也一起否决”的返回，让成熟的事件序列能逐渐拉回时钟。未改成每帧视觉相位必须进入 4° 窗口才允许发令。

新增回归：恒定 4.50 rad/s，4.56 rad/s 初始设定，运行中给视觉相位施加持续 30° 偏移。原实现长时间保留约 30° 误差并断言失败；修复后双方向都能恢复。此合成测试证明恢复机制，不代表靶车会真实瞬移 30°。

## 2. 已确认：多个“延时/预测”参数不控制当前实际发令

当前生效的是固定中心周期分支，不同参数的用途如下。

| 参数 | 检查时值 | 当前用途 |
| --- | ---: | --- |
| `xuc_periodic_phase_offset_ms` | 460 | 实际发令相位，按学习后的单面周期取模 |
| `xuc_periodic_every_n_faces` | 2 | 每隔两次装甲板经过请求一次；门槛拒绝会使实际间隔更长 |
| `xuc_event_fixed_omega_rad_s` | 4.56 | 时钟初始周期和方向配合；成熟事件会校准周期 |
| `xuc_event_fire_delay_s` | 0.640 | 周期分支中的预计到达/显示计算，不决定实际发令时刻 |
| `high_speed_delay_time` / `low_speed_delay_time` | 0.330 / 0.330 | 原生 Aimer 预测；当前高速周期分支用中心跟随和独立时钟发令 |
| `xuc_direct_yaw_boresight_correction_deg` | -1.30 | 实际水平目标角修正 |
| `xuc_direct_yaw_impact_correction_deg` | -1.05 | 实际水平目标角修正；与前一项合计 -2.35° |
| `xuc_directional_yaw_step_deg` | 0 | 逐发实验补偿已由用户关闭；保持为 0 |
| `sentinel_fire_min_interval_ms` | 200 | 串口请求频率下限；不是当前约 0.7 秒节拍的来源 |

以初始 4.56 rad/s 为例，单面周期为 344.473 ms，460 ms 取模后为 115.527 ms。增加一个单面周期会回到相近的发令相位，不能把不断增加该值当成无限延后同一块板。

因此，以前调整 `xuc_event_fire_delay_s` 却没有真实弹着变化，有明确的代码路径解释。此次没有擅自把它改成生效延迟，否则会改变已有 460 ms 相位的含义。

## 3. 已确认：原“相位误差接近零”属于内部时钟自检

`Solution::command_phase_error_at()` 用调度时钟自己的锚点、角速度和计划发令相位计算误差。在该时钟的到期时刻发送，结果自然接近零；这不能独立证明靶板同步准确。

原诊断 JSON 已有 `periodic_visual_phase_error_deg`，但普通发令日志没有同时突出它。本次新增：

- `PERIODIC_FIRE` 日志同时打印 `visual_clock_error_deg`。
- `periodic_clock_large_residual_updates` / 日志 `large_residual_updates`：大残差恢复更新计数。
- `gyro_model_phase_estimated_tx_deg`：把最近一帧视觉模型外推到串口发送时刻，和原时钟估计分别记录。
- 启动日志明确周期发令依据为视觉过中心加手动相位，事件延时不参与该模式发令。

这些量仍是软件估计，没有命名为实测出膛或实测弹着角度。

## 4. 仍需验证：真实出膛/飞行时序未闭环

小电脑当前收到 0x83 的拨弹完成计数。它证明电机走过一个单发步长，不能证明弹丸已在该时刻离开摩擦轮。

上一轮匹配到的“发送请求到主机观察到完成步长”中位数约 52 ms，包含通信和反馈观察过程。不能拿它直接替换为真实出膛延迟；同样也没有证据证明现有 640 ms 就是真实延迟。

当前 0x82 详细发射诊断不可用，无法从现有记录独立还原 MCU 收包、开始拨弹、出膛的全链路。此项是残余未知，未通过猜测参数处理。

固定靶不会因晚到几十毫秒而横向走开，所以固定靶命中无法验证旋转靶时序。

## 5. 仍需验证：摩擦轮许可宽于弹速稳定条件

电控 `control.h`：目标转速 6500 rpm，`friction_ready_ratio = 0.8`，差速限制 300 rpm；`control.cpp` 还检查左右转向、温度、CAN 反馈新鲜和拨弹电机状态。

这允许正向轮速度达到 5200 rpm、反向轮达到 -5200 rpm 后具备拨弹条件。它能防止未起转时发射，但不能证明每发均为实测 21.8～22.2 m/s。不能假定摩擦轮转速与弹速严格线性。

量级示例：3 m 距离，22 m/s 直线飞行约 136 ms；假如弹速实际变为 20 m/s，则约 150 ms，差 14 ms。在 4.56 rad/s 下相当于约 3.6° 的靶车旋转相位。这里只展示敏感度，不是认定本机已经发生这种掉速。

未在没有逐发转速记录的情况下改许可阈值或 PID，以免把新的拒发/掉频与原问题混在一起。

## 6. 仍需验证：旋转中心估计和图像时间有误差

同一轮新鲜高速模型记录：中心方位角第 5/95 百分位约 0.009° / 1.534°，中心估计平面速度中位数约 0.118 m/s。若靶车物理中心静止，这些量包含估计误差；仍无法把它们全部归因于滤波器，因为没有独立中心真值。

当前高速跟随使用估计的整车中心，中心并没有因配置名为 fixed-center 而被硬锁定。其角度滤波时间常数 60 ms，会影响中心变化时的枪口参考，但不会直接覆盖手动发令相位。

海康帧时间取 SDK 提供图像时的主机时刻，再减半个曝光时间和配置的传输补偿；当前没有使用相机设备时间做已验证同步。程序队列只保留最新一帧，不能仅凭队列设计证明曝光时刻已准确。

姿态日志的时间不确定度中位数约 30.8 ms，其中含代码设定的 30 ms 保守传输预算。它不是测得的固定 30.8 ms 延迟，不能直接作为补偿值。

原始装甲板法向与滤波相位也存在明显帧间差异。说明视觉模型本身并非绝对真值；本次时钟回放改善不能证明物理过中心相位已准确。

## 7. 本次未发现对应错误的环节

- 启动器从正式 YAML 生成运行配置；没有发现覆盖本次水平/周期参数的分支。正式参数修改需要重启进程。
- 角度修正进入当前中心跟随命令；前轮累计补偿变化后，实际 IMU yaw 也改变。没有发现修正总被零值覆盖的通用路径。
- 高速周期发射的 yaw 门槛比较枪口跟踪误差，没有强制装甲板必须回到旧的未补偿像素中心；未发现该门槛把水平补偿反向抵消。
- `Aimer` 的未来装甲板预测结果在当前高速中心跟随分支被替换为中心参考，不会在正常新鲜模型帧上再额外叠一份未来装甲板 yaw。
- 外环 PI 当前高速不继续积分，保留的静态积分最多 0.8°；不能据此认定它会无限累积。最新旋转记录的积分为零。
- V2 上位机发送目标相对参考 IMU 的误差，下位机以同一参考一次性重建绝对目标，未发现旧版重复累加角度问题。
- TIM2 已有预分频更新事件，微秒时基修复仍在；没有恢复旧的错误时基。
- 控制任务周期 5 ms。正常短请求触发一次拨弹；持续请求超过 300 ms 才进入 125 ms 连发分支。普通周期短脉冲不符合该长按条件。
- 已有串口发送互斥、启动会话/序号/参考有效期检查和请求频率限制；本次未发现固定一秒额外等待。发送成功仍不等于 MCU 接受或弹丸出膛。
- 当前发令帧的云台跟踪误差中位数约 0.170°、第 95 百分位约 0.497°。表明枪口姿态基本跟随软件目标，不能证明目标相位计算正确。

“未发现”仅表示本次源码与现有记录没有支持相应故障，不代表对所有现场条件作无缺陷保证。
