# 省赛开机自动任务

唯一小电脑工程：`/home/rcsdart/rm27`。新增任务服务：`rm27-mission.service`。
原有 `rm27-navigation.service` 继续负责雷达、里程计和地图定位。

## 使用流程

1. 继续使用现有支持 Sentinel NAV 的电控固件。本次切换上位机计数不需要重新烧录。
2. 小电脑开机自动启动定位、视觉和任务管理器。
3. 底盘中心放在已配准的 P00，朝首段方向；小Y、P轴先处于希望导航期间保持的位置。遥控器先保持 STOP（左上右中），摇杆回中。
4. 等任务状态为 `READY_WAIT_BOTH_UP`，再拨双上。无需按 Enter。
5. 去程保持云台，不启用自瞄、摩擦轮或拨弹；任务点停稳后，才允许原视觉流程控制和发射。
6. 本轮成功下发第31次拨弹请求后启用丢失检测，连续超过5秒没有新装甲板观测即返航；或者累计下发50次请求直接返航。请求数不代表电机实际拨完、弹丸出膛或命中。
7. 返航前撤销自瞄、摩擦轮及拨弹许可，等待至少250毫秒，再沿审核过的去程反向回P00。回到起点停稳、撤销底盘许可。
8. 完成后不会在双上档位自动循环。下一轮需重新在P00准备、切回其他档位后再拨双上。

开机时已经双上也不会直接出发，需要准备完成后重新切档。当前保留导航任务原来的300秒总期限；超时、通信/定位/相机失效、遥控退出AUTO等中止任务，不盲目继续行驶或自动重启任务。中止后查明原因，由现场人员重新启动服务。未满足31次且一直未发现目标时，不触发“5秒返航”，最后会受到300秒总期限限制。

## 状态查看

```bash
python3 ~/rm27/navigation/mission/status.py
cat ~/rm27/navigation/logs/mission/status.json
systemctl status rm27-mission.service --no-pager
journalctl -u rm27-mission.service -n 60 --no-pager
```

优先使用 `status.py`：只有本轮新鲜的定位、任务与监管状态同时合格，且处于非双上待启动档，才显示“已就绪”。`systemctl` 的 active 仅表示监管进程在运行，不表示已经允许出发。后面的早期修改章节是历史记录；当前启动恢复策略见本文末尾 2026-10-29 小节。

主要状态：`WAIT_READY`、`READY_WAIT_BOTH_UP`、`OUTBOUND`、`STOP_TASK`、`TASK_DWELL`（执行视觉任务）、`RETURNING`、`STOP_HOME`、`RELEASING`、`DONE`、`FAULT`。

`sent_requests` 为本轮成功下发的拨弹请求数。`return_reason` 为 `sent_50_requests` 或 `armor_lost_over_5s_after_30_requests`。等待状态中的 `error` 和 `wait_reason` 会指出缺少的就绪条件；`start_checks` 显示起点、朝向与停稳检查。

如需手工单独调自瞄，先由现场人员停止任务服务，再使用原自瞄入口，防止重复占用相机和串口：

```bash
sudo systemctl stop rm27-mission.service
```

## 参数与保持行为

任务阈值在已有正式导航路线 `navigation/map_route/global_plan.json` 的 `competition_task` 中：

| 参数 | 当前值 | 含义 |
|---|---:|---|
| `lost_target_check_after_requests` | 30 | 本轮请求数严格超过30，即从31次开始 |
| `return_at_sent_requests` | 50 | 本轮请求数达到50立即结束任务 |
| `armor_lost_s` | 5.0 | 连续超过该秒数没有识别结果 |

修改路线配置时需要同步 `map_route/sources.json` 的哈希；任务启动前会验证。路线、最高1.80米/秒、加减速、P00配准沿用导航其三的当前设置。旧手动纯导航命令仍有自己的5秒停留语义；本服务使用外部任务完成条件，不受那5秒停留值触发。

本次计数修改没有改动视觉正式配置 `configs/standard.yaml`，沿用用户当前保存的角度、节拍与颜色。开机服务只在启动器生成的运行缓存中启用无窗口模式。

小Y采用现有GM6020位置环，P轴采用现有达妙位置模式。进入导航无自瞄许可的阶段，各轴仅记录一次真实位置，随后固定目标保持；反馈代次变化时重新确认。任务阶段交给原视觉控制，返航阶段重新记录并保持。没有添加左右扫描，没有修改PID、摩擦轮转速、初始化角度或限位。

## 通信与计数口径

- `standard` 是唯一实体串口所有者；导航管理器通过本机原子文件交接命令，AIM与NAV整帧串行写入同一串口。
- 当前计数来自 `XucSender` 成功写出的带 `fire_request` 的完整 AIM 帧。尝试发送、限频、无许可、过期请求与写入失败均不加一；普通瞄准、摩擦轮和 NAV 帧也不计入。
- 本机 IPC 为 schema 2，标记 `count_source=host_tx`；`fire_requests_sent` 是当前视觉进程累计成功下发数，`sent_requests` 是任务管理器减去本轮起始基线后的数量。
- 任务开始记录请求数基线。视觉进程重启、主控重启或计数倒退仍使当前任务失效，不自动续跑。
- 不再用 `0x83` 的计数、编码器代次、步长或新鲜度决定出发、发射和返航。若该消息存在，仍可只读取其中的 NAV 最近序号帮助上位机单独重启后衔接序号；消息缺失不阻止新主控会话启动 NAV。主控未重启且也不提供 NAV 序号时，无法凭空保证序号衔接，主控拒绝命令仍会中止。
- 串口出口在任务许可和本机计数上限处同步拦截，达到50次后即使 Python 状态刷新稍晚，也不会继续下发第51次。电控姿态、LINK_STATUS、AUTO档位以及100毫秒任务许可仍需有效；相机卡住不会被当作正常丢失装甲板。
- Python管理器停止刷新命令后，本机100毫秒许可失效并撤销NAV；主控原有租约仍作为第二层保护。软件线程或进程完全卡死时，依靠主控租约到期停止，不能承诺没有调度延迟。

## 到点交接时间调整

自动比赛入口已改成短窗口：取最近0.5秒，至少4个不同源时间戳、跨度至少0.35秒；速度最大6厘米/秒、均值3厘米/秒，位置直径3厘米、航向范围约2度、最大角速度约4.6度/秒。命令仍为零且观测通过后才进入任务，持续移动或转动仍不会放行。静止后的确认预计约0.4～0.6秒，实际依赖刹停及反馈；不是固定倒计时后无条件开火。

### 查明的问题

| 问题 | 原因与证据 | 本次处理 |
| --- | --- | --- |
| 电控或相机晚到，任务入口直接失败 | 日志显示开机缺少相机/串口，旧监管马上启动两个子进程；预检失败后服务 `Restart=no`，之后不会再准备 | 监管先只读检查设备及权限，持续等待；稳定接入后才启动一次视觉与任务管理器 |
| 雷达晚接后出现反复重启 | 原监控等待地址120秒即抛异常，独立小电脑持续每两分钟重启导航 | 等待物理网线载波及正确地址，没有硬件等待期限；地址就绪后才开始独立75秒定位启动预算 |

| 相机或串口线程停止，但主程序还活着 | 单纯看PID无法识别无新帧、无新MCU姿态 | 检查视觉状态、源帧时间及link/pose；初次流允许20秒建立，连续异常达到5秒后准备期重建 |

### 当前启动顺序

1. systemd分别启动导航监管与任务监管，二者不依赖图形桌面登录。
2. 导航监管等待雷达网线载波和已有静态地址；随后启动雷达、FAST-LIO、底盘坐标换算及地图后端，检查实时数据和地图定位。
3. 任务监管等待配置中的相机USB和串口by-id链接及权限，稳定至少1秒后启动唯一视觉进程和任务管理器。
4. 视觉负责实体串口，任务管理器只用schema 2本地IPC。定位、MCU和画面新鲜、P00位置/朝向/停稳合格后，仍需准备阶段的非AUTO及新的双上边沿。
5. 执行去程、任务点视觉任务和返航。31次后连续丢失目标超过5秒或50次host_tx返航的规则不变。

准备期子进程退出、USB重枚举或数据停更，可自动清理并重新准备。停止会话时先删除任务命令文件、停止任务管理器，等待300ms超过已有主控租约，再停止视觉进程组；失败请求不会保留为待执行任务。

**任务已经开始后出现故障，保持 `FAULT_LATCHED`，不会自动继续路线。** 监管意外退出留下的同一开机活动标记也会锁定。现场检查原因后，可显式执行：

```bash
sudo systemctl restart rm27-mission.service
```

显式停止/重启会在清理完子进程和撤销许可后清除活动标记。新会话仍需回P00、保持非AUTO并重新拨双上；不会沿用上轮双上状态。完成返航时正常清除活动标记。断电后的新boot_id不会采信上一次开机的旧状态文件。
